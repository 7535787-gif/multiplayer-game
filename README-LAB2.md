5. Проблема з this
Проблема виникає, якщо метод передати як callback:
window.addEventListener('keydown', ship.fire)

У цьому випадку передається сама функція, а не виклик методу з ship як receiver. Тому значення this визначається способом виклику callback і може бути неправильним.
Основні правила this:
1. new — this є новим створеним об'єктом.
2. Явний виклик — call(), apply(), bind() задають this явно.
3. Неявний виклик — у object.method() this є object.
4. Звичайний виклик — у strict mode this дорівнює undefined.
Стрілочні функції не мають власного this і беруть його із зовнішнього контексту.
У проєкті проблема виправлена через wrapper:
window.addEventListener('keydown', (event) => {
  ship.fire(world)
})

Також можливі альтернативи:
ship.fire.bind(ship)

або класове поле зі стрілочною функцією.
Wrapper не створює окрему функцію для кожного Ship, а bind() створює прив'язану функцію, тому вибір залежить від ситуації.

6. Астероїди та колізії
Asteroid є сутністю з власними:
- координатами;
- швидкістю;
- радіусом;
- HP.
Колізії винесені в окрему систему collision.js.
Основна перевірка — зіткнення двох кіл:
distance <= radiusA + radiusB

Для пошуку пар використовується наївний алгоритм O(n²), що достатньо для поточного етапу лабораторної.
Окремо обробляються колізії:
- куля → астероїд;
- куля → корабель;
- корабель → астероїд;
- корабель → pickup.
Кулі завдають шкоди кораблям та астероїдам.

7. Приватне HP, вибухи, respawn та score
HP корабля зберігається у приватному полі:
#hp = 100

Для доступу використовується:
get hp()

При знищенні корабля створюється Explosion.
Explosion містить частинки, які існують обмежений час і поступово зникають.
Після знищення корабля через 2 секунди створюється новий корабель у випадковій безпечній точці.
За знищення астероїда збільшується рахунок:
world.score += 100

Рахунок та HP відображаються на HUD.

8. Композиція: Homing та Pickup
Чому не глибока ієрархія?
Якби реалізовувати homing через наслідування, могла б виникнути структура:
Entity
└── MovingEntity
    ├── Ship
    ├── Bullet
    │   └── HomingBullet
    └── Asteroid
        └── HomingAsteroid

Це створює зайві класи та прив'язує поведінку до конкретного типу об'єкта.
Наприклад, якщо пізніше знадобиться самонавідний pickup або інша сутність із homing, довелося б створювати нові класи.
Тому для додаткової поведінки використовується композиція.
Homing
У homing.js створюється поведінка:
createHoming(target)

Вона має метод:
update(entity, dt)

і змінює швидкість об'єкта в напрямку цілі.
Поведінка передається сутності як властивість:
this.homing = homing

Тому одна й та сама поведінка може бути підключена до кулі або астероїда без створення нових класів.
У грі клавіша H створює самонавідну кулю, яка прямує до астероїда.
Pickup
Pickup не є Ship і не успадковує його поведінку.
Pickup:
- нерухомий;
- має радіус колізії;
- взаємодіє з кораблем;
- має окрему поведінку.
Для поточної реалізації використовується лікувальна поведінка:
createHealing(25)

Вона передається в Pickup як об'єкт поведінки.
При зіткненні pickup застосовує цю поведінку до корабля:
behavior.apply(target)

Таким чином, механіку pickup можна змінювати без створення нових класів-нащадків.

9. Експеримент з прототипами
У JavaScript методи класів знаходяться у prototype.
Для:
const ship = new Ship(...)

ланцюжок має вигляд:
ship
 ↓
Ship.prototype
 ↓
Entity.prototype
 ↓
Object.prototype
 ↓
null

Наприклад, при зверненні до ship.update JavaScript спочатку шукає властивість у самому ship, потім у Ship.prototype, а потім у Entity.prototype.
Це показує, що методи класів не копіюються в кожен об'єкт окремо, а знаходяться в прототипі.

Reflection
1. Чому виникла проблема з this?
this визначається способом виклику функції, а не місцем, де метод був оголошений. При передачі ship.fire як callback метод викликається вже не як ship.fire(), тому this може бути неправильним.
Виправлення — wrapper, bind() або стрілочне поле класу.
2. Чому Map, а не звичайний об'єкт?
Map зручний для entity store, тому що:
- дозволяє використовувати числові ID без перетворення;
- має .size;
- підтримує безпосередню ітерацію;
- не має проблеми з успадкованими властивостями об'єкта;
- зручний для частих додавань та видалень.
3. Чому композиція краща для homing?
Homing є поведінкою, а не окремим видом сутності. Його можна підключити до кулі або астероїда без створення HomingBullet та HomingAsteroid.
Це дозволяє уникнути глибокої ієрархії та повторного коду.
